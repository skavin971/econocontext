Declarative cost-context management

EconoContext

Context is not housekeeping and cost is not an invoice. They are one decision — where work runs, which versioned state it sees, and whether to reuse, repair, recompute or start fresh.

Part I — What this is a picture and ten lines of Python

What it is, and how you call it

A library you hand a task, some data and a budget. It decides how the work gets done.

You bring an agent: its tools, and a way of checking whether the work came out right. EconoContext sits underneath and answers a question your agent never has to ask — for this next piece of work, which worker should do it, what state should that worker see, and should it continue, repair, reuse or start over.

Calling it

# intended shape — see the note below for what runs today
import econocontext

async with econocontext.open(tools=my_tools, verify=my_verifier) as eco:
    result = await eco.run(
        prompt="Fix the failing ledger test",
        data="./repo",
        limits=econocontext.Limits(max_cost=1.00, context_tokens=32_000),
        quality=econocontext.Quality(needs_exact_bytes=True),
    )

# every plan it chose, what it predicted, what it actually cost,
# and what it rejected to get there
for d in result.decisions:
    print(d.mode, d.view, d.predicted_cost, d.actual_cost, d.why_not)

Three things are worth noticing. You declare the work and the constraints — never a context strategy, a chunk size or a sub-agent. quality is a floor, not a target: needs_exact_bytes tells the planner that a paraphrase of a file is not an acceptable substitute for the file, which rules out cheaper plans it would otherwise take. And the decisions come back inspectable, with the price it expected next to the price it paid.

What runs today. A working prototype implements the planner, cost model, optimizer, assembler and versioned state store against a live model. The representation layer, cross-agent asking and the learned policies described later are designed, not built. Evaluation is in progress; no measured figures are claimed on this page.
Part II — The problem why a token budget gets this wrong

What you are actually paying for

Everything in a context was computed once. A stateless API makes you pay for it again, every turn.

An agent reads a file, reasons about it, runs a test. All of that becomes tokens sitting in a context window. Each of those tokens was paid for when it arrived — and then paid for again on the next call, and the next, because the model holds no memory between requests. A context is not storage. It is a subscription to everything you have already bought.

So the question is never "is this context too big?" It is: is keeping this cheaper than getting it back?

That reframing does the work. Everything an agent harness argues about — compaction, eviction, summarisation, sub-agents, cache reuse — is one question about recovery cost, asked in different places. And it cannot be answered about memory alone, because where the work runs decides what has to be kept at all.

And the obvious proxy is not merely imprecise — it is inverted

Providers bill disjoint categories at different rates: uncached input, cache reads, cache writes, output. Once cached input is an order of magnitude cheaper, a larger retained context can be cheaper than a smaller fresh one.

So what is a plan worth? Four things

What a plan costs =

      getting ready           retrieving, compressing, re-sending what isn't cached
    + doing the work          the model calls and tool calls this plan needs
    + taking it back          the parent receiving the result and checking it
    + what it leaves behind   a heavier context, or work you'll have to redo later

The fourth line is the one that is normally missing, and it is the one that decides most arguments. A plan that looks cheapest today is often the one that quietly loads the main context with material every subsequent turn must pay to re-send. Spelled out in billing terms:

C(P) = retrieve + compress      getting ready
     + LLM + tools             doing the work — uncached input, cache reads/writes, output
     + integration             taking it back
     + future + recompute + repair   what it leaves behind

Eight terms, four ideas. Latency is estimated alongside and never folded into money — a cheaper plan that takes three times as long is a different trade, and the caller should see both.

The four columns below are always these four. Every table on the rest of this page prices one decision using exactly this breakdown, so the same arithmetic is visible each time. Figures use $1.50 per million uncached input, $0.15 cached, $9.00 output — illustrative, and the shape of the argument does not depend on the exact rates.

How systems decide what to keep today

Two good answers to a question next door to ours.

This is not an empty field, and the useful prior work is worth stating plainly rather than talked around.

Kalypso does not try to predict which information matters. It watches the machine — memory pressure, queue depth, which prefixes are still resident — estimates what each job will need, admits work accordingly, and corrects from what actually happened. It does not ask the model what matters; it watches the meter. That control principle is exactly right, and we take it.

ClawVM goes further into memory. It makes state explicit as typed pages, each with a minimum fidelity it may never degrade below, and scores every page by a weighted sum over pin status, membership in the active plan, recency, scope and what it would cost to recompute — importance as likely reuse × cost to get it back. Pages degrade Full → Compressed → Structured → Pointer instead of being silently dropped. A filing cabinet where every folder knows how hard it would be to recreate. That ladder is theirs, and we use it.

Both answer the same question: what should stay resident? Neither answers the two questions this page is about.

Neither decides where the work should run. Kalypso schedules over an operator graph known in advance; agent operations do not exist until the agent invents them. ClawVM ranks pages but has no notion of a worker, so it can never trade a page against running the work somewhere that already has it.

And neither attaches a price to its own decision. ClawVM's budget is tokens, so it will re-order a context to save 500 tokens and invalidate a 20,000-token cached prefix without ever seeing the loss — because in tokens, it won.

That gap is the whole of what follows: keep the typed pages, keep the control loop, and put a price on the decision.

Part III — The idea one move, stated once

One decision, three axes

Choose them apart and they get each other wrong.

WHERE IT RUNS

Which worker performs this operation — the main agent, one that already has relevant context, or a new scoped one.

WHAT IT SEES

Which versioned state is materialized for it, and in which representation: full bytes, compressed, structured, or a pointer.

HOW IT PROCEEDS

Reuse an existing result, continue a live worker, repair one whose state went stale, or start fresh.

They are not independent, and each pair proves it. Put the work in a worker that already holds the file, and the file no longer has to be materialized — where changed what it sees. Hand a worker a pointer instead of the bytes, and continuing it becomes impossible for anything needing the bytes — what it sees changed how it proceeds. Start fresh and every piece of evidence must be paid for again — how changed what.

So: the agent declares the work it needs done, not how to obtain it. A planner enumerates the combinations, prices each one whole, and picks the cheapest that clears a quality floor.

The next three sections take one axis each. Each ends in a price. They are in this order because the third one collapses into the first two.

Part IV — The three axes one running example: a failing ledger test

What it sees — state that knows what it costs to get back

Not all tokens have equal future value.

Throughout this part: a five-module ledger repository with a failing test, test_reconcile. Worker W3 has already read accounts.py — evidence E7, 8,000 tokens — and produced a diagnosis, R3.

Memory is versioned objects rather than one long conversation: policies, plans, evidence, tool results, worker results. Each may be materialized several ways, and each records how it can be recovered and at what cost, plus how likely it is to be wanted again.

The four actions on E7, priced

The planner is choosing how to carry accounts.py through the next few turns. Compression here is a small local model, not a frontier call, so preparing it is cheap but not free.

Action on E7Getting readyDoing the work Taking it backLeaves behindTotal
Keep it in full — 8,000 tok—$0.0120—$0.0048$0.0168
Keep it compressed — 2,000 tok$0.0008$0.0030—$0.0012$0.0050

Drop it, re-read if needed———$0.0060$0.0060

Leaves behind is doing two different jobs in that table. For the first two rows it is the cost of re-sending the material on every remaining turn at the cached rate. For the last two it is the expected cost of getting it back — a 40% chance of needing it, times what recovery costs.

On price, POINTER wins at $0.0049. And then it loses, immediately:

The operation is apply a patch to accounts.py. A patch needs exact bytes. A pointer, a summary and a compression are all interpretations of the file — none of them is the file. Both cheap rows are infeasible, not merely risky, and FULL is chosen at 3.4× the price of the option the optimizer preferred.

This is why representations belong to the optimizer rather than to a storage policy. There is no fixed answer to "how should we store a file". There is only an answer for this operation, which knows what fidelity it requires.

ClawVM contributes the typed pages, the four-rung ladder and the minimum-fidelity invariant that makes the last paragraph enforceable rather than aspirational. Our addition is the table above: the ladder is priced against a specific operation, not scored by a standing weight.

How it proceeds — four actions, each with a price

The same keeping-versus-getting-back question, asked about work instead of memory.

REUSE

A valid, sufficient existing result is returned directly. No worker model call at all — frequently the cheapest action available.

CONTINUE

Preserve an existing worker and its context. Attractive when its state is still valid and a substantial prefix can be reused.

REPAIR

Keep the useful prior computation, refresh only what changed — a worker that knows a subsystem where one file moved v8 → v9.

FRESH

Give up the reuse advantage and scope a new worker. The fallback when prior state is irrelevant, too stale, too costly or unsafe to carry.

Back to the ledger. A fix has just landed: accounts.py moved v8 → v9, and test_reconcile still fails. W3 understands this module, but everything it knows is about v8.

ActionGetting readyDoing the work Taking it backLeaves behindTotal
REUSE R3, W3's v8 diagnosis——$0.0008invalidgate
CONTINUE W3 as it stands—$0.0170$0.0008invalidgate
REPAIR W3 — refresh only E7$0.0032$0.0180$0.0008$0.0040$0.0260
FRESH worker on v9$0.0120$0.0210$0.0008$0.0070$0.0408

REPAIR wins by a clear margin, and the two struck-out rows matter as much as the winner. Reusing a superseded diagnosis and continuing a worker whose state describes the wrong version are not cheap options here — they are invalid ones. Version validity is a gate, not a discount. A system that treats staleness as a quality risk to be traded against price will eventually trade it away.

And REPAIR is not a rule, it is a price. Move the change from one module to four, and REPAIR's preparation rises from $0.0032 to roughly $0.029 — the same action, now costing $0.052 against FRESH's $0.041. FRESH wins. Nothing about the situation changed except how much moved.

Where it runs — when the cheapest copy is in another agent's context

The axis that turns out to be the other two.

W3 now holds accounts.py at v9, warm, in a context the provider will serve at the cached rate. A second worker, W5, is checking the test harness and needs to know what post_entry validates.

The ordinary answer is that W5 reads the file. But the harness mediates every tool call, so it sees something the agent cannot: this file is already in someone's head.

Because the harness owns every tool call, each read registers a versioned evidence object recording which workers hold it, at which version, in which representation. So a read request is not an instruction — it is a request for information, with candidates:

CandidateGetting readyDoing the work Taking it backLeaves behindTotal
Materialize the bytes in W5—$0.0120—$0.0036$0.0156
Ask W3, which already holds it—$0.0034$0.0003$0.0002$0.0039
REUSE — this was already asked——$0.0003$0.0002$0.0005

Three gates, or this is just wishful thinking

FIDELITY

An answer is an interpretation, not the bytes. If the operation must apply a patch or quote exactly, asking is infeasible — the same floor that ruled out POINTER earlier.

VERSION

A holder of v8 cannot answer questions about v9. The registry records versions precisely so this fails loudly instead of returning confident, obsolete answers.

LATENCY

Asking serializes on the holder, which may be busy. Token cost falls; wall-clock time may not. That is a real trade, and it is priced as one rather than assumed away.

The consequence is structural: no single context ever holds the whole codebase. The system's knowledge is chunked across workers and addressed by question rather than by bytes — and the harness keeps the index of who knows what.

Which closes Part IV. A worker holding evidence in warm context is simply one more representation of that evidence — another rung on the ladder from §6, with its own recovery cost and its own fidelity limit. "Where the work runs" and "what it sees" are not two decisions that interact. They are one decision, and that is why they have to be priced together.

PARSER contributes the shape: assign chunks to scoped readers, query them repeatedly, let a lead agent reason over what comes back — including reusing a reader that already holds a chunk. Our addition is that asking is a priced candidate rather than the fixed policy: sometimes reading the file really is cheaper, and the planner should be able to say so. We also owe the measurement PARSER's design implies — what a selective approach misses by not querying every reader. ClawVM supplies the justification for doing this in the harness at all: it already assembles prompts, mediates tools and observes lifecycle events, so it is the one place that can see the opportunity.

Part V — Priced together, and made real from candidates to a rendered request

One plan, priced whole, corrected by measurement

Chosen together, because chosen apart they get each other wrong.

Back to the failing test, with all three axes live at once. The operation: explain why test_reconcile fails at v9.

Stop after the first three columns and A is cheapest, at $0.0162 against B's $0.0220. Add the fourth and A is the most expensive plan on the table. Nothing about A changed — we simply stopped pretending the 8,000 tokens it parks in the root context are free on every turn that follows.

That reversal is the argument for the fourth term. A planner without it will reliably choose the plan that loads the main context, because loading the main context is always cheap right now and expensive forever afterwards. It is also, not coincidentally, how agents die: A is the plan that walks a 32,000-token budget into the wall.

Cheapest feasible, not cheapest

Minimizing cost alone has a degenerate answer: do nothing, spend nothing, achieve nothing. So the objective is minimize expected cost subject to a quality floor — min C(P) s.t. Q(P) ≥ Q_min.

Feasibility is checked before economics: required evidence present, minimum fidelity satisfied, dependency and version validity, context window, tool and permission constraints. A plan that violates one is removed, not discounted — that is what struck out two rows in §7 and both cheap representations in §6. Among what survives, the lowest expected whole-task cost wins, and every rejection is recorded with its reason, which is what d.why_not returns to the caller.

Relevance outranks cheapness. Evidence ranking answers which information is plausibly useful; the optimizer answers which plan uses that information economically. Run in that order, a warm cache cannot make irrelevant evidence win.

The estimates correct themselves

None of these numbers are known in advance; they are predictions. So the planner runs as a closed loop, and — this matters for the cost of running it — none of the loop spends a model call. Choosing is arithmetic over recorded profiles.

A worker keeps persistent logical state — task, evidence versions seen, results produced, dependencies, current context, status — and a reuse state: prefix fingerprint, context tokens, observed cached tokens, last reuse time, prior cache hits. That last group is what makes the estimates honest: a worker that keeps promising reusable tokens and returning cached=0 stops being attractive.

On physical memory. A self-hosted engine can expose real KV residency, and where it does, that is a stronger signal worth using. It is deliberately not a requirement: behind a hosted API the planner works from observed reuse instead. The resource being managed here is not KV — it is previously computed agent state. Cache reuse is one reason preserving a worker pays; its reasoning, results and evidence are the others.

Which is the whole relationship in one line: the agent names the result it needs, and the planner chooses the access path — the same relationship a query optimizer has to SQL, where the application never names an index scan.

Assembly, ordering, and why a reorder costs money

The prices above only hold if the rendered request behaves the way they assumed.

Planning and rendering are separate jobs, and keeping them separate is what makes the system auditable. The planner chooses content; the assembler renders it and never chooses. Every assembled request is content-addressed with a manifest — renderer version, worker revision, every evidence reference with its source and version, the token estimate, the configuration fingerprint — and can be reconstructed byte-for-byte afterwards. Any decision on this page can be replayed and checked.

The assembler runs on every turn. What it does not do on every turn is re-order.

Four zones, ordered by how fast they change

FROZEN

Instructions and tool schemas. Identical for the life of the worker.

SLOW

Task statement, constraints, standing policy. Changes at most a few times per run.

WARM

Reusable evidence, appended when a plan pays for it. Grows; does not shuffle.

VOLATILE

The current request and its observations. Different every turn, and last on purpose.

The ordering rule is one sentence: the longest-lived content occupies the longest-stable prefix, and new content appends within its own zone. Everything a provider can serve from cache is therefore at the front, and everything that changes is behind it.

The cost of moving something

A reorder is not forbidden. It is a candidate, and it has a price — because a prefix that diverges at position k means every token after k is charged again at the uncached rate.

ClawVM re-runs a greedy upgrade loop every turn, admitting pages by marginal utility per token until the budget is spent — and may re-order freely, because ordering is free when your budget is measured in tokens. Our addition is the figure above: under per-token billing, layout is an expense, and a rebuild is a candidate the optimizer has to justify like any other.

Where the learned models attach

ClawVM's scoring function is a weighted sum with hand-set weights, plus an oracle variant that looks three turns ahead. That is not a weakness — it is a precise description of the seams where learning belongs, and it is why the three models we intend to train are three and not one.

ModelReplacesPredicts
ForecastingHand-set recency and recomputation weights; the fixed lookahead horizonOutput length, how many calls remain, whether evidence will be wanted again, how the view will change — each with an uncertainty, because a confident wrong estimate is worse than a wide one
Evidence selectionThe greedy utility-per-token upgrade loopWhich optional evidence earns its place, and which placements are permitted without breaking the prefix
Planner policyNothing — there is no equivalentWhether to retrieve, continue, resume, repair, delegate, or ask a worker that already holds the answer

The third row is the point. Kalypso and ClawVM have no notion of choosing where work runs, so there is nothing to replace — that model exists only because the planner does. And whatever any of the three decide, deterministic code always performs the final render, and deterministic checks always enforce versions, permissions and context limits. A learned policy may propose; it never gets to violate an invariant.

Direction

One selection interface, three implementations, in order.

VersionHow it choosesThe question it answers
Fixed rulesSimple triggers for retrieval, continuation and delegationDoes the architecture help before adding an optimizer?
Cost-basedCompares candidates using measured profiles and simple forecastsDoes explicitly comparing costs improve the decision?
LearnedThe three models above, informed by the same cost modelDoes learning improve on the cost-based selector?

The interface does not change between them, which is what makes the comparison meaningful. Learning is admitted only once traces show consistent estimation error — a later method, not a prerequisite, and not a second headline claim.

Evaluation compares task success, total cost, latency and context growth under matched budgets against a flat agent with tuned append-only execution and compaction, with ablations separating the contribution of delegation, of learning and of cache reuse. Failed runs count toward total cost; known subtotals are reported separately from completeness. Cost at matched quality is the only comparison that means anything — an arm that is cheaper because it failed is not cheaper.
