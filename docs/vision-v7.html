Declarative cost-context management

EconoContext

Context is not housekeeping and cost is not an invoice. They are one decision — where work runs, which versioned state it sees, and whether to reuse, repair, recompute or start fresh.

Part I — What this is a picture and ten lines of Python

What it is, and how you call it

A library you hand a task, some data and a budget. It decides how the work gets done.

You bring an agent: its tools, and a way of checking whether the work came out right. EconoContext sits underneath and answers a question your agent never has to ask — for this next piece of work, which worker should do it, what state should it see, and should it continue, repair, reuse or start over.

Calling it

# intended shape — see the note below for what runs today
import econocontext

async with econocontext.open(tools=my_tools, verify=my_verifier) as eco:
    result = await eco.run(
        prompt="Find and fix the failing test",
        data="./repo",
        limits=econocontext.Limits(max_cost=1.00, context_tokens=32_000),
        quality=econocontext.Quality(needs_exact_bytes=True),
    )

# every plan it chose, what it predicted, what it actually cost,
# and what it rejected to get there
for d in result.decisions:
    print(d.mode, d.view, d.predicted_cost, d.actual_cost, d.why_not)
  • You declare the work and the constraints — never a context strategy, a chunk size or a sub-agent.
  • quality is a floor, not a target. needs_exact_bytes says a paraphrase of a file will not substitute for the file, which rules out cheaper plans the planner would otherwise take.
  • Decisions come back inspectable — the price it expected, next to the price it paid.
What runs today.
  • Built — planner, cost model, optimizer, assembler and versioned state store, against a live model.
  • Designed, not built — the representation layer, the REPAIR mode, cross-agent asking, and the learned policies described later.
  • Evaluation is in progress. No measured figures are claimed on this page.
Part II — The problem why a token budget gets this wrong

What you are actually paying for

Everything in a context was computed once. A stateless API makes you pay for it again, every turn.

  • An agent reads a file, reasons about it, runs a test. All of that becomes tokens sitting in a context window.
  • Each token was paid for when it arrived — and again on the next call, and the next, because the model holds no memory between requests.
  • A context is not storage. It is a subscription to everything you have already bought.

So the question is never "is this context too big?" It is: is keeping this cheaper than getting it back?

  • That reframing does the work. Compaction, eviction, summarisation, sub-agents, cache reuse — every one is the same recovery-cost question, asked somewhere different.
  • And it cannot be answered about memory alone, because where the work runs decides what has to be kept at all.

And the obvious proxy is not merely imprecise — it is inverted

  • Providers bill disjoint categories at different rates: uncached input, cache reads, cache writes, output.
  • Once cached input is an order of magnitude cheaper, a larger retained context can cost less than a smaller fresh one.

What a price is made of

If it is not a token count, it has to be something — and something that survives changing provider.

  • The same 8,000 tokens cost an order of magnitude more processed fresh than served from the provider's cache. Nothing about the tokens changed.
  • So the unit of pricing is not tokens. It is billing categories — uncached input, cache reads, cache writes, output, reasoning.

That sounds like a solved problem until you try it across two providers.

Three places the meter disagrees with itself

ProblemWhat actually happensWhat the harness does
Reasoning tokens OpenAI counts them inside completion_tokens. Google's OpenAI-compatible endpoints report them separately and leave them out. Disambiguate with the provider's own total_tokens: reasoning joins billed output only when prompt + completion + reasoning equals the reported total. Never charged twice, never missed.
Missing cache detail Google omits prompt_tokens_details entirely on calls where nothing was cached — so "no cache field" and "no cache" are indistinguishable. Charge the whole prompt at the uncached rate and flag cache_reported: false. An upper bound, not a refusal — dropping those calls instead understated a measured run by about 2.5×.
Cache writes Some providers charge a premium to create a cache entry, so a cache can cost more than it saves on a prefix used once. Recorded as needing provider-specific normalization before it counts as a known charge. The model tracks what it does not yet know rather than assuming zero.

None of this is exotic. It is what happens the first time you point a cost model at a second vendor, and it is why the categories have to be normalized before anything is priced.

The shape that survives changing vendor

cost  =  Σ  ratei  ×  resourcei
  • The planner reasons in resources — tokens processed fresh, tokens served from cache, tokens generated, seconds of local work.
  • The rate vector is deployment configuration. Change provider and you change the vector; the same plan is re-priced and not one line of planning logic moves.

It is also what makes an open or self-hosted model tractable, where there is no price per token at all. What costs money there is time on a machine you are renting — and it decomposes the same way:

PREFILL

Work proportional to fresh input. A cache hit does not discount it — it removes it. This is the same resource as "uncached input", priced in FLOPs instead of dollars.

DECODE

Time proportional to output, bounded by memory bandwidth rather than arithmetic. The analogue of the output rate.

KV OCCUPANCY

Retained context holds memory, memory caps batch size, and batch size sets cost per request. A hosted API prices this for you; self-hosted, it is yours.

  • Same sum, different vector, different units — seconds rather than dollars, then seconds times what the instance costs.
  • This part is designed, not built. The prototype prices hosted endpoints. The resource decomposition is what would make self-hosting a configuration change rather than a rewrite.

What we actually compute

Four things added together — the same four every time:

What a plan costs =

      getting ready           retrieving, compressing, re-sending what isn't cached
    + doing the work          the model calls and tool calls this plan needs
    + taking it back          the parent receiving the result and checking it
    + what it leaves behind   a heavier context, or work you'll have to redo later
  • The fourth line is the one normally missing, and it decides most arguments. The plan that looks cheapest today is usually the one quietly loading the main context with material every later turn must pay to re-send.
  • Latency is estimated alongside and never folded into money. A cheaper plan that takes three times as long is a different trade, and the caller should see both.

"Doing the work", in detail

That one term is where the cache argument lives, so it is worth unpacking. It answers two questions in order.

1 · How many INPUT tokens will this plan send, in total?

      context size  ×  number of calls       the whole context is re-sent on every call
    + output that piles up along the way     what the model writes becomes input later

2 · What do those tokens cost?

      input tokens   ×  blended input rate   part fresh, part served from cache
    + output tokens  ×  output rate
  • That first number is a token count, not money. It is "how much input will this plan push through the API across its whole life". The rate turns it into money, which is why it is multiplied and not added.
  • Context size × calls is the subscription, made arithmetic. A plan needing three calls pays for its context three times, not once. This is the single biggest term in almost every estimate.
  • The output term is an average. Across three calls the first carries none of what the model has written, the last carries nearly all of it — so on average about half of it is being re-sent. That is all the ÷ 2 means.
  • The blended rate is where tokens stop being the unit. Same token count, different money, depending only on how much of it the provider serves from cache.

That cache fraction: predicted, not measured

Nothing can know before a call whether the provider will serve the prefix from cache. So it is a forecast — and the estimator is deliberately pessimistic about it.

  • Estimated from history — what past calls carrying a matching prefix actually came back with.
  • Fewer than three matching samples and it credits nothing. No observations, no discount.
  • Capped twice: never more than 10% of input, and never more than the shared prefix is actually long.
  • Corrected afterwards. What the call really cost feeds the next estimate — which is the entire reason the planner runs as a loop.
  • It is a claim about billing, never about what is physically resident in GPU memory.

So it would rather understate a saving than invent one — which biases our own approach to look worse than it is. That is the correct direction for a tool whose job is to stop you over-trusting a retained context.

Every number carries its unit.
  • An estimate records its basis — USD when real rates are configured, fixed-fallback when they are not.
  • Numbers with different bases are never compared, and a run without prices reports itself as not cost-optimized rather than inventing a dollar figure.
  • A cost model that quietly mixes units is worse than no cost model, because it still produces a ranking.
Part III — The idea one move, stated once

One decision, three axes

Choose them apart and they get each other wrong.

WHERE IT RUNS

Which worker performs this operation — the main agent, one that already has relevant context, or a new scoped one.

WHAT IT SEES

Which versioned state is materialized for it, and in which representation: full bytes, compressed, structured, or a pointer.

HOW IT PROCEEDS

Reuse an existing result, continue a live worker, repair one whose state went stale, or start fresh.

They are not independent, and each pair proves it:

  • Put the work in a worker that already holds the file and the file never has to be materialized — where changed what it sees.
  • Hand a worker a pointer instead of the bytes and continuing it becomes impossible for anything needing the bytes — what it sees changed how it proceeds.
  • Start fresh and every piece of evidence must be paid for again — how changed what.

So: the agent declares the work it needs done, not how to obtain it. A planner enumerates the combinations, prices each one whole, and picks the cheapest that clears a quality floor.

The next three sections take one axis each — in this order, because the third collapses into the first two.

Part IV — The three axes each ends in a price

What it sees — state that knows what it costs to get back

Not all tokens have equal future value.

Memory is versioned objects rather than one long conversation — evidence, plans, results — and each one records how it can be recovered, at what cost, and how likely it is to be wanted again.

Four options for any one piece of evidence

  • Keep it in full, keep a compression, keep a pointer and fetch on demand, or drop it and re-read later.
  • Keeping costs a small certain amount — re-sending it every remaining turn at the cached rate. Dropping costs an uncertain larger one — the chance you need it again, times what recovery costs.
  • On price the pointer usually wins: 30 tokens against 8,000. Then it loses — an apply a patch operation needs exact bytes, and a pointer or a summary is an interpretation of the file, not the file.

Price is the objective, not the decision. Options that cannot meet the required fidelity are removed before anything is compared, so the run gets more expensive on purpose. Which is why representations belong to the optimizer, not to a storage policy.

The typed pages and the four-rung ladder are ClawVM's. Our addition: the ladder is priced against a specific operation, not scored by a standing weight.

How it proceeds — four actions, each with a price

The same keeping-versus-getting-back question, asked about work instead of memory.

REUSE

A valid, sufficient existing result is returned directly. No worker model call at all — frequently the cheapest action available.

CONTINUE

Preserve an existing worker and its context. Attractive when its state is still valid and a substantial prefix can be reused.

REPAIR

Keep the useful prior computation, refresh only what changed — a worker that knows a subsystem where one file moved v8 → v9.

FRESH

Give up the reuse advantage and scope a new worker. The fallback when prior state is irrelevant, too stale, too costly or unsafe to carry.

  • A worker's accumulated reasoning is a stored asset like any other. These four are four answers to what it is worth.
  • Two of them are frequently not options at all. Reusing a superseded result, or continuing a worker whose state describes a version that has since changed, are invalid rather than cheap.
  • REPAIR is why none of this can be a rule. Refreshing one changed file under a worker that knows the subsystem wins easily; if the change touches most of what it knows, starting fresh is cheaper. Nothing changed but how much moved.

Version validity is a gate, not a discount. A system that weighs staleness against price will eventually trade it away, because stale is always cheaper.

Where it runs — when the cheapest copy is in another agent's context

The axis that turns out to be the other two.

  • One worker already holds a file, warm, in a context the provider serves at the cached rate.
  • A second worker needs something that file answers. The ordinary answer is that it reads the file.
  • But the harness mediates every tool call, so it sees what neither agent can: this file is already in someone's head.
  • Every read registers a versioned evidence object recording which workers hold it, at which version, in which representation.
  • So a read stops being an instruction and becomes a request for information, with candidates: materialize the bytes, ask a holder, or reuse an earlier answer to the same question.
  • Asking is usually several times cheaper — the holder's input is almost all cached prefix, and only a short answer crosses over.
  • Three gates keep it honest: fidelity — an answer is an interpretation, not the bytes; version — a holder of the old file must fail loudly, not answer confidently; latency — asking serializes on the holder, so token cost falls but wall-clock may not.

No single context ever holds the whole codebase. Knowledge is chunked across workers and addressed by question rather than by bytes — which is why "where the work runs" and "what it sees" are one decision, not two.

Scoped readers queried repeatedly is PARSER's shape. Our addition: asking is a priced candidate rather than the fixed policy — sometimes reading really is cheaper. ClawVM supplies why this belongs in the harness: it already mediates every tool call.

Part V — Priced together, and made real from candidates to a rendered request

One plan, priced whole, corrected by measurement

Chosen together, because chosen apart they get each other wrong.

  • A plan names all three at once: which worker, which view of the state, which mode. Each choice is locally defensible; only the combination has a price.

Rank plans on the first three terms and the one that loads the main context wins. Add the fourth and it becomes the most expensive on the table — the tokens it parks there are not free on any later turn. It is also the plan that walks a fixed budget into the wall.

Cheapest feasible, not cheapest

  • Minimizing cost alone has a degenerate answer — do nothing, spend nothing, achieve nothing. So the objective is minimize expected cost subject to a quality floor.
  • Feasibility is checked before economics: required evidence present, minimum fidelity satisfied, version validity, context window, permissions. A plan that violates one is removed, not discounted.
  • Among what survives, the lowest expected whole-task cost wins, and every rejection is recorded with its reason.
  • Relevance outranks cheapness. Evidence ranking decides what is plausibly useful; the optimizer decides which plan uses it economically. In that order, a warm cache cannot make irrelevant evidence win.

The estimates correct themselves

  • None of these numbers are known in advance — they are predictions, so the planner runs as a closed loop.
  • None of that loop spends a model call. Choosing is arithmetic over recorded profiles, which is what makes planning cheap enough to be worth doing.
  • A worker keeps what it has seen, what it produced, and its observed cache behaviour. That last part keeps the estimates honest — a worker that keeps promising reusable tokens and returning cached=0 stops being attractive.
  • The resource being managed is not the KV cache — it is previously computed agent state. Where a self-hosted engine exposes real residency that is a stronger signal worth using, but it is deliberately not a requirement.

Which is the whole relationship in one line: the agent names the result it needs, and the planner chooses the access path — the same relationship a query optimizer has to SQL, where the application never names an index scan.

Assembly, ordering, and what a rebuild costs

Every price above assumed the prefix would still be there. This is the layer that keeps that true.

  • The planner chooses content; the assembler renders it and never chooses. Every request is content-addressed with a manifest and reconstructible byte-for-byte, so any decision here can be replayed.
  • On an ordinary turn nothing moves. New content is appended at the end, every byte before it is identical to last turn, and the provider serves that prefix from cache.
  • The assembler runs on every turn — on almost all of them its job is to add, not to rearrange.

Four zones, ordered by how fast they change

FROZEN

Instructions and tool schemas. Identical for the life of the worker.

SLOW

Task statement, constraints, standing policy. Changes at most a few times per run.

WARM

Reusable evidence, appended when a plan pays for it. Grows; does not shuffle.

VOLATILE

The current request and its observations. Different every turn, and last on purpose.

The ordering is not tidiness. Inserting into zone k invalidates only the zones after k — and everything after WARM was changing this turn anyway, so adding evidence there costs nothing extra. That is the whole reason zones are sorted by rate of change.

So which turns rebuild?

Four things, and nothing else:

CauseWhy it breaks the prefix
A representation changesEvidence already placed as FULL is swapped for COMPRESSED. The bytes at that position are different, so everything after them is different too.
A version advancesA file the worker already read is edited, and the new bytes replace the old ones in place. This is the common one in a coding run: every patch the agent applies to a file it has already read.
CompactionSomething in the middle is dropped or summarised to reclaim room. By construction it is not at the end.
A deliberate reorderMoving evidence for relevance, or regrouping to shorten the prompt. The only one of the four that is chosen rather than forced.
  • The first three are consequences of work the agent is already doing. Only the fourth is a decision — and it is the one the optimizer has to justify.

The cost of moving something

  • A reorder is not forbidden — it is a candidate with a price, because a prefix that diverges at position k means every token after k is charged again at the uncached rate.

ClawVM re-orders freely, because ordering is free when the budget is tokens. Our addition is the figure above: under per-token billing, layout is an expense.

What this layer is ultimately for

  • Today the placement rule is fixed: append within your zone. That is deliberately dumb, and the right place to start — a fixed rule you can price beats a clever one you cannot.
  • The goal is that placement becomes a priced decision like every other one here: a policy choosing not only what enters the context but where it may go, with rebuild cost as a term it has to justify.
  • Deterministic code always performs the final render. A policy proposes a layout; it never emits the bytes and never violates an invariant.
