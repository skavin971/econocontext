Does EconoContext cut an agent's cost?

Experiment results, October 6, 2026

Yes, so far. In the same agent on the same tasks, EconoContext lowered the cost of a run and did not lower the pass rate. The samples are small (see the caveats).

Setup

Agent harnessOur own small agent loop (Python) with 4 tools: bash, read file, write file, submit
ModelGemini 3.6 Flash (Google Vertex)
BenchmarkTBLite (Terminal-Bench Lite), 10 fixed tasks
RunnerHarbor; each run in a fresh Docker container
GradingEach task's own tests: pass or fail
LimitsSame for every setup: at most 60 steps; tool output cut at 30,000 characters
IsolationEach run starts with an empty session database, deleted at the end; nothing carries over
CostGemini's bill for every call in the run. Jev's cost is counted separately

The three setups

SetupWhat it does
No EconoContextThe agent keeps everything and re-sends its whole conversation on every call
EconoContextJev (a classifier) predicts what the agent still needs; a price decides what to keep, shrink or summarize. The price counts on the provider's cache
EconoContext, no cache guessThe same, but the price ignores the cache, which we cannot see or control on a closed model

EconoContext sends 20% fewer input tokens; the model writes about the same. Gemini served about 69% of input from its cache in both setups. In the first repeat, most of the saving came from compaction: when Jev says a part of the work is finished, the model summarizes it and the details leave the conversation (a full copy stays in the session database).

What EconoContext did

ActionEconoContext (30 runs)No cache guess (10 runs)
Big tool output: keep a slice or a preview instead of all of it78 of 10658 of 77
Compaction: the model summarizes a finished part72
Drop a finished big item06
Don't repeat an identical call31

Counting on the cache made keeping everything look cheap, so the first setup never dropped an item. Ignoring the cache let that rule act.

How we checked

  • Every model call re-priced from Gemini's raw token counts; call counts and token totals match the agent's own log.
  • Every pass/fail matches the grader's own file.
  • Every run had its own empty database and its own container; on the first repeat we checked that no run borrowed another run's cache.
  • 10 runs never reached the grader (one harness crash; nine stopped by our own gateway's daily token cap). They are not counted, and their reruns are.

Caveats

  • Small samples: 30 pairs and 10 pairs.
  • The no-cache-guess runs used only the 5 longest tasks, and the no-EconoContext runs they are compared with ran earlier the same day.
  • Malicious package cost more with EconoContext (+23.7%, one failure); not yet analysed.
  • The pass-rate gains (sales data, bandit) are hints, not findings.
