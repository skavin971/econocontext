Declarative cost-context management

EconoContext

Context is not housekeeping and cost is not an invoice. They are one decision — where work runs, which versioned state it sees, and whether to reuse, repair, recompute or start fresh.

Part I — What this is a picture and ten lines of Python

What it is, and how you call it

A library you hand a task, some data and a budget. It decides how the work gets done.

You bring an agent: its tools, and a way of checking whether the work came out right. EconoContext sits underneath and answers a question your agent never has to ask — for this next piece of work, which worker should do it, what state should that worker see, and should it continue, repair, reuse or start over.

Calling it

# intended shape — see the note below for what runs today
import econocontext

async with econocontext.open(tools=my_tools, verify=my_verifier) as eco:
    result = await eco.run(
        prompt="Find and fix the failing test",
        data="./repo",
        limits=econocontext.Limits(max_cost=1.00, context_tokens=32_000),
        quality=econocontext.Quality(needs_exact_bytes=True),
    )

# every plan it chose, what it predicted, what it actually cost,
# and what it rejected to get there
for d in result.decisions:
    print(d.mode, d.view, d.predicted_cost, d.actual_cost, d.why_not)

Three things are worth noticing. You declare the work and the constraints — never a context strategy, a chunk size or a sub-agent. quality is a floor, not a target: needs_exact_bytes tells the planner that a paraphrase of a file is not an acceptable substitute for the file, which rules out cheaper plans it would otherwise take. And the decisions come back inspectable, with the price it expected next to the price it paid.

What runs today. A working prototype implements the planner, cost model, optimizer, assembler and versioned state store against a live model. The representation layer, the REPAIR mode, cross-agent asking and the learned policies described later are designed, not built. Evaluation is in progress; no measured figures are claimed on this page.
Part II — The problem why a token budget gets this wrong

What you are actually paying for

Everything in a context was computed once. A stateless API makes you pay for it again, every turn.

An agent reads a file, reasons about it, runs a test. All of that becomes tokens sitting in a context window. Each of those tokens was paid for when it arrived — and then paid for again on the next call, and the next, because the model holds no memory between requests. A context is not storage. It is a subscription to everything you have already bought.

So the question is never "is this context too big?" It is: is keeping this cheaper than getting it back?

That reframing does the work. Everything an agent harness argues about — compaction, eviction, summarisation, sub-agents, cache reuse — is one question about recovery cost, asked in different places. And it cannot be answered about memory alone, because where the work runs decides what has to be kept at all.

And the obvious proxy is not merely imprecise — it is inverted

Providers bill disjoint categories at different rates: uncached input, cache reads, cache writes, output. Once cached input is an order of magnitude cheaper, a larger retained context can be cheaper than a smaller fresh one.

So what is a plan worth? Four things

What a plan costs =

      getting ready           retrieving, compressing, re-sending what isn't cached
    + doing the work          the model calls and tool calls this plan needs
    + taking it back          the parent receiving the result and checking it
    + what it leaves behind   a heavier context, or work you'll have to redo later

The fourth line is the one that is normally missing, and it is the one that decides most arguments. A plan that looks cheapest today is often the one that quietly loads the main context with material every subsequent turn must pay to re-send. Spelled out in billing terms:

C(P) = retrieve + compress      getting ready
     + LLM + tools             doing the work — uncached input, cache reads/writes, output
     + integration             taking it back
     + future + recompute + repair   what it leaves behind

Eight terms, four ideas. Latency is estimated alongside and never folded into money — a cheaper plan that takes three times as long is a different trade, and the caller should see both.

Every table on this page uses these four headings, so the same breakdown is visible each time; a table drops a column only where that term is genuinely zero for the decision being made. Figures use $1.50 per million uncached input, $0.15 cached, $9.00 output — illustrative, and the shape of the argument does not depend on the exact rates.

What a price is made of

If it is not a token count, it has to be something — and something that survives changing provider.

The same 8,000 tokens cost an order of magnitude more when the provider has to process them fresh than when it serves them from its own cache. Nothing about the tokens changed. So the unit of pricing is not tokens — it is billing categories: uncached input, cache reads, cache writes, output, and reasoning tokens.

That sounds like a solved problem until you try it across two providers.

Three places the meter disagrees with itself

ProblemWhat actually happensWhat the harness does
Reasoning tokens OpenAI counts them inside completion_tokens. Google's OpenAI-compatible endpoints report them separately and leave them out. Disambiguate with the provider's own total_tokens: reasoning joins billed output only when prompt + completion + reasoning equals the reported total. Never charged twice, never missed.
Missing cache detail Google omits prompt_tokens_details entirely on calls where nothing was cached — so "no cache field" and "no cache" are indistinguishable. Charge the whole prompt at the uncached rate and flag cache_reported: false. An upper bound, not a refusal — dropping those calls instead understated a measured run by about 2.5×.
Cache writes Some providers charge a premium to create a cache entry, so a cache can cost more than it saves on a prefix used once. Recorded as needing provider-specific normalization before it counts as a known charge. The model tracks what it does not yet know rather than assuming zero.

None of this is exotic. It is what happens the first time you point a cost model at a second vendor, and it is why the categories have to be normalized before anything is priced.

The shape that survives changing vendor

cost  =  Σ  ratei  ×  resourcei

The planner reasons in resources — tokens that must be processed fresh, tokens served from a cache, tokens generated, seconds of local work. The rate vector is deployment configuration. Change provider and you change the vector; the same plan is re-priced and not one line of planning logic moves.

That is also what makes an open or self-hosted model tractable, where there is no price per token at all. What costs money there is time on a machine you are renting, and it decomposes the same way:

PREFILL

Work proportional to fresh input. A cache hit does not discount it — it removes it. This is the same resource as "uncached input", priced in FLOPs instead of dollars.

DECODE

Time proportional to output, bounded by memory bandwidth rather than arithmetic. The analogue of the output rate.

KV OCCUPANCY

Retained context holds memory, memory caps batch size, and batch size sets cost per request. A hosted API prices this for you; self-hosted, it is yours.

Same sum, different vector, different units — seconds rather than dollars, then seconds times what the instance costs. This part is designed, not built. The prototype prices hosted endpoints; the resource decomposition is what makes the self-hosted case a configuration change rather than a rewrite.

What the estimate actually computes

retained    = size × calls  +  output × (calls − 1) / 2
execution   = retained × [ (1 − f) × uncached  +  f × cached ]  +  output × output_rate
integration = parent_tokens × uncached  +  256 × output_rate   when a parent receives it
additional  = P(more work) × cost(more work)

Two parts of that line carry the whole argument. size × calls is the subscription, made arithmetic: this plan needs several calls, and the context is re-sent on every one of them. The bracket is where tokens stop being the unit — identical retained, different money, entirely through f.

Where f comes from, and how little it claims

The cache fraction is a prediction, and the estimator is deliberately pessimistic about it:

  • Observed cache fractions are collected per compatible prefix fingerprint, from completed runs.
  • Fewer than three matching samples and f is zero. No observations, no credit.
  • Credit is capped at 10% of input, and again at the measured size of the compatible prefix.

So the model would rather understate a saving than invent one. It is an uncertain prediction that a prefix will be served from cache — never proof that a session is resident, and no claim about physical memory. When the prediction is wrong, the measured result corrects it.

Every number carries its unit. An estimate records its basis: USD when real rates are configured, fixed-fallback when they are not. Numbers with different bases are never compared, and a run without prices reports itself as not cost-optimized rather than inventing a dollar figure. A cost model that quietly mixes units is worse than no cost model, because it still produces a ranking.
Part III — The idea one move, stated once

One decision, three axes

Choose them apart and they get each other wrong.

WHERE IT RUNS

Which worker performs this operation — the main agent, one that already has relevant context, or a new scoped one.

WHAT IT SEES

Which versioned state is materialized for it, and in which representation: full bytes, compressed, structured, or a pointer.

HOW IT PROCEEDS

Reuse an existing result, continue a live worker, repair one whose state went stale, or start fresh.

They are not independent, and each pair proves it. Put the work in a worker that already holds the file, and the file no longer has to be materialized — where changed what it sees. Hand a worker a pointer instead of the bytes, and continuing it becomes impossible for anything needing the bytes — what it sees changed how it proceeds. Start fresh and every piece of evidence must be paid for again — how changed what.

So: the agent declares the work it needs done, not how to obtain it. A planner enumerates the combinations, prices each one whole, and picks the cheapest that clears a quality floor.

The next three sections take one axis each. Each ends in a price. They are in this order because the third one collapses into the first two.

Part IV — The three axes each ends in a price

What it sees — state that knows what it costs to get back

Not all tokens have equal future value.

Memory is versioned objects rather than one long conversation: policies, plans, evidence, tool results, worker results. Each may be materialized several ways, and each records how it can be recovered and at what cost, plus how likely it is to be wanted again.

The four options, and why the cheapest one loses

For any one piece of evidence the planner has four options: keep it in full, keep a compression of it, keep only a pointer and fetch on demand, or drop it and re-read later. Each is priced on the same four terms.

Two of those terms do different jobs, and the distinction matters. Keeping something costs you re-sending it on every remaining turn, at the cached rate — a small certain cost. Dropping something costs you expected recovery: the chance you need it again, times what getting it back would cost — a larger uncertain one.

On price, the pointer usually wins. It is 30 tokens against 8,000. And then, often, it loses immediately.

If the operation is apply a patch, it needs exact bytes. A pointer, a summary and a compression are all interpretations of the file — none of them is the file. Those options are infeasible, not merely risky, so they are removed before anything is compared, and the most expensive option is chosen.

That is the clearest thing on this page about what kind of system this is. Price is the objective, not the decision. A constraint the optimizer cannot trade against overruled it, and the run got more expensive on purpose — which is correct, because the cheaper options would not have produced a working patch at any price.

This is also why representations belong to the optimizer rather than to a storage policy. There is no fixed answer to "how should we store a file". There is only an answer for this operation, which knows what fidelity it requires.

How it proceeds — four actions, each with a price

The same keeping-versus-getting-back question, asked about work instead of memory.

REUSE

A valid, sufficient existing result is returned directly. No worker model call at all — frequently the cheapest action available.

CONTINUE

Preserve an existing worker and its context. Attractive when its state is still valid and a substantial prefix can be reused.

REPAIR

Keep the useful prior computation, refresh only what changed — a worker that knows a subsystem where one file moved v8 → v9.

FRESH

Give up the reuse advantage and scope a new worker. The fallback when prior state is irrelevant, too stale, too costly or unsafe to carry.

The link back is exact: this is the same keeping-versus-getting-back question, asked about work instead of memory. A worker's accumulated reasoning is a stored asset like any other, and the four actions are four answers to what it is worth.

Two of them are frequently not options at all. Reusing a superseded result, or continuing a worker whose state describes a version that has since changed, are not cheap choices — they are invalid ones. Version validity is a gate, not a discount.

That distinction is load-bearing. A system that treats staleness as a quality risk to be weighed against price will, sooner or later, trade it away — because stale is always cheaper. So it is checked before economics, and a plan that fails it is removed rather than discounted.

REPAIR is the interesting one, and the reason none of this can be a rule. Refresh one changed file under a worker that knows the subsystem and it wins easily. Let the change touch most of what the worker knows and the same action now costs more than starting fresh. Nothing about the situation changed except how much moved — which is precisely the kind of judgement a price can make and a heuristic cannot.

Where it runs — when the cheapest copy is in another agent's context

The axis that turns out to be the other two.

Suppose one worker already holds a file — warm, in a context the provider will serve at the cached rate. A second worker now needs to know something that file answers.

The ordinary answer is that the second worker reads it. But the harness mediates every tool call, so it sees something neither agent can: this file is already in someone's head.

Because the harness owns every tool call, each read registers a versioned evidence object recording which workers hold it, at which version, in which representation. So a read request stops being an instruction and becomes a request for information, with candidates: materialize the bytes, ask a worker that already holds them, or reuse an answer to the same question asked earlier.

Asking is typically several times cheaper, because the holder's input is almost entirely a cached prefix it has already been charged for once, and only a short answer crosses into the asking worker.

Three gates, or this is just wishful thinking

FIDELITY

An answer is an interpretation, not the bytes. If the operation must apply a patch or quote exactly, asking is infeasible — the same floor that ruled out POINTER earlier.

VERSION

A holder of v8 cannot answer questions about v9. The registry records versions precisely so this fails loudly instead of returning confident, obsolete answers.

LATENCY

Asking serializes on the holder, which may be busy. Token cost falls; wall-clock time may not. That is a real trade, and it is priced as one rather than assumed away.

The consequence is structural: no single context ever holds the whole codebase. The system's knowledge is chunked across workers and addressed by question rather than by bytes — and the harness keeps the index of who knows what.

Which closes Part IV. A worker holding evidence in warm context is simply one more representation of that evidence — another rung on the ladder from What it sees, with its own recovery cost and its own fidelity limit. "Where the work runs" and "what it sees" are not two decisions that interact. They are one decision, and that is why they have to be priced together.

PARSER contributes the shape: assign chunks to scoped readers, query them repeatedly, let a lead agent reason over what comes back — including reusing a reader that already holds a chunk. Our addition is that asking is a priced candidate rather than the fixed policy: sometimes reading the file really is cheaper, and the planner should be able to say so. We also owe the measurement PARSER's design implies — what a selective approach misses by not querying every reader. ClawVM supplies the justification for doing this in the harness at all: it already assembles prompts, mediates tools and observes lifecycle events, so it is the one place that can see the opportunity.

Part V — Priced together, and made real from candidates to a rendered request

One plan, priced whole, corrected by measurement

Chosen together, because chosen apart they get each other wrong.

A plan names all three at once: which worker, which view of the state, which mode. Reusing a worker saves preparation but may carry a large or outdated context. A narrower view is cheaper now and may cost a follow-up later. Each choice is locally defensible; only the combination has a price.

Rank a set of plans on the first three terms alone and the one that loads the main context wins. Add the fourth term and it becomes the most expensive plan on the table. Nothing about it changed — we simply stopped pretending the tokens it parks in the root context are free on every turn that follows.

That reversal is the whole argument for what it leaves behind. A planner without it will reliably pick the plan that loads the main context, because loading the main context is always cheap right now and expensive forever afterwards. It is also, not coincidentally, how agents die: that is the plan that walks a fixed budget into the wall.

Cheapest feasible, not cheapest

Minimizing cost alone has a degenerate answer: do nothing, spend nothing, achieve nothing. So the objective is minimize expected cost subject to a quality floor — min C(P) s.t. Q(P) ≥ Q_min.

Feasibility is checked before economics: required evidence present, minimum fidelity satisfied, dependency and version validity, context window, tool and permission constraints. A plan that violates one is removed, not discounted — that is what struck out the stale worker and the two cheap representations earlier in this part. Among what survives, the lowest expected whole-task cost wins, and every rejection is recorded with its reason, which is what d.why_not returns to the caller.

Relevance outranks cheapness. Evidence ranking answers which information is plausibly useful; the optimizer answers which plan uses that information economically. Run in that order, a warm cache cannot make irrelevant evidence win.

The estimates correct themselves

None of these numbers are known in advance; they are predictions. So the planner runs as a closed loop, and — this matters for the cost of running it — none of the loop spends a model call. Choosing is arithmetic over recorded profiles.

A worker keeps persistent state — what it has seen, what it produced, and a reuse state of observed cache behaviour. That last part is what keeps the estimates honest: a worker that keeps promising reusable tokens and returning cached=0 stops being attractive.

On physical memory. A self-hosted engine can expose real KV residency, and where it does, that is a stronger signal worth using. It is deliberately not a requirement: behind a hosted API the planner works from observed reuse instead. The resource being managed here is not KV — it is previously computed agent state. Cache reuse is one reason preserving a worker pays; its reasoning, results and evidence are the others.

Which is the whole relationship in one line: the agent names the result it needs, and the planner chooses the access path — the same relationship a query optimizer has to SQL, where the application never names an index scan.

Assembly, ordering, and what a rebuild costs

Every price above assumed the prefix would still be there. This is the layer that keeps that true.

Planning and rendering are separate jobs, and keeping them separate is what makes the system auditable. The planner chooses content; the assembler renders it and never chooses. Every assembled request is content-addressed with a manifest — renderer version, worker revision, every evidence reference with its source and version, the token estimate, the configuration fingerprint — and can be reconstructed byte-for-byte afterwards. Any decision on this page can be replayed and checked.

What happens on an ordinary turn

Nothing moves. New content is appended at the end, and every byte before it is identical to the last turn, so the provider serves that prefix from its cache. The assembler runs on every turn — it is not an occasional cleanup pass — but on almost all of them its job is to add, not to rearrange.

Four zones, ordered by how fast they change

FROZEN

Instructions and tool schemas. Identical for the life of the worker.

SLOW

Task statement, constraints, standing policy. Changes at most a few times per run.

WARM

Reusable evidence, appended when a plan pays for it. Grows; does not shuffle.

VOLATILE

The current request and its observations. Different every turn, and last on purpose.

The ordering is not tidiness. Inserting into zone k invalidates only the zones after k — so because everything after WARM was going to change this turn anyway, adding evidence to WARM costs nothing that was not already being re-sent.

That is the whole reason the zones are sorted by rate of change. It makes the common case — a plan paying to bring new evidence into a worker — free of any cache penalty, without anyone having to reason about it.

So which turns rebuild?

Four things, and nothing else:

CauseWhy it breaks the prefix
A representation changesEvidence already placed as FULL is swapped for COMPRESSED. The bytes at that position are different, so everything after them is different too.
A version advancesA file the worker already read is edited, and the new bytes replace the old ones in place. This is the common one in a coding run: every patch the agent applies to a file it has already read.
CompactionSomething in the middle is dropped or summarised to reclaim room. By construction it is not at the end.
A deliberate reorderMoving evidence for relevance, or regrouping to shorten the prompt. The only one of the four that is chosen rather than forced.

The first three are consequences of work the agent is already doing. Only the fourth is a decision — and it is the one the optimizer has to justify.

The cost of moving something

A reorder is not forbidden. It is a candidate, and it has a price — because a prefix that diverges at position k means every token after k is charged again at the uncached rate.

ClawVM re-runs a greedy upgrade loop every turn, admitting pages by marginal utility per token until the budget is spent — and may re-order freely, because ordering is free when your budget is measured in tokens. Our addition is the figure above: under per-token billing, layout is an expense, and a rebuild is a candidate the optimizer has to justify like any other.

What this layer is ultimately for

Today the placement rule is fixed: append within your zone. That is deliberately dumb, and it is the right thing to start with, because a fixed rule you can price beats a clever one you cannot.

The goal is that placement becomes a priced decision like every other one on this page — a policy choosing not only what enters the context but where it is allowed to go, with the rebuild cost as a term it has to justify rather than a rule it has to obey.

Right now the assembler protects the cache by never doing anything interesting. The version worth building lets it act when, and only when, the arithmetic says so: reordering for relevance when the prefix it breaks was about to be rebuilt anyway, compacting early when the remaining turns will repay it.

One thing does not move. Deterministic code always performs the final render. A policy proposes a layout; it never emits the bytes, never violates an invariant, and never produces a prompt that cannot be reconstructed from its manifest.
