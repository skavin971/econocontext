Background

How agents are billed

An agent like Claude Code works in turns. On every turn it sends the whole conversation so far to the model: the instructions, every file it read, every command output. The provider bills all of it, every turn.

Providers soften this with a cache. If the start of this turn's conversation is exactly the same as last turn's, that repeated part is billed at about a tenth of the price. But the match is strict: it stops at the first change. Change something early, and everything after it is billed at full price again. Some providers (Anthropic) even charge extra, 1.25 times the price, to write text into the cache.

The core ideaWhat an agent keeps, where it keeps it, and when it removes things all change the bill, and the provider's cache rules decide by how much. Nobody prices those choices today.

Step 2

Our angle: helpers, not just trimming

Should EconoContext manage only one conversation, or also decide when to use helper agents?

Correction. Step 1's idea, cache-aware removal inside one conversation, is already published: TokenPilot and CAPC both do it and report 49 to 87% savings. So that alone is not our contribution.

What those papers share is that they manage one conversation. None decides where work happens. That is the open space.

A helper agent is removal done in advance

Say the agent needs to read 40 files to find one function.

  • Read it in the main conversation: all 40 files join the main conversation and are re-sent on every remaining turn. Removing them later is expensive, because they sit early.
  • Hand it to a helper: the files go into a short conversation that ends after a few turns. Only a short answer comes back. The reading is thrown away for free when the helper finishes.

So choosing a helper is choosing to remove the material before it ever arrives. Removal and placement are one decision, made at two different moments, and one cost model can price both.

EconoContext does not write agents for anyone; it decides where each piece of work's text lives.
Step 3

Is it new?

Has anyone already priced where work happens against the cache bill?

We sorted about fifteen papers and systems by what they decide:

  • Price cache-aware choices: TokenPilot, CAPC. Always one conversation.
  • Decide where work happens: Context-Folding (trained with reinforcement learning), SearchSwarm (trained by fine-tuning), and today's helper agents (the model's own judgment). None prices the cache bill.
  • Nothing found in both groups. That overlap is where EconoContext sits. "Plausibly open" is the honest level: we read abstracts and summaries, not every full paper.

Step 4

The model, in plain words

Can we state the idea precisely enough to make predictions?

Each turn costs r·h + w·(n − h) + o·m: the cached part h at the cheap read price r, the rest of the n tokens at the write price w, and m output tokens at price o. Nine results follow from that one line.

R1

Cost grows with the square of session length. Every turn re-sends everything before it, so twice the turns costs about four times as much. Caching makes it cheaper, but still quadratic. Only removing or relocating text changes that.

R2one-time cost = (w − r)·τ − r·ℓ

Removing a block costs what sits after it. Removing ℓ tokens re-bills the τ tokens after it once, and saves r·ℓ on every later turn.

R3

Remove now or never. Waiting only adds more text after the block, which makes removing it dearer, while leaving fewer turns to earn it back.

R4ℓ* = ((w − r)/r)·Δ

Below a size threshold, "wait and see" never removes anything. Δ is how much the conversation grows per turn. For blocks smaller than ℓ*, the price of removing keeps rising faster than the rent of keeping it. So the choice has to be made when the text arrives, from a forecast. That is placement.

R5

The threshold differs 19-fold between providers. About 30,000 tokens at Anthropic's 1-hour prices; about 1,600 where the cache discount is only 50%. So which lever matters most (placement or removal) depends on the provider, and one ratio predicts which.

R6

Remove in batches. Once you pay to break the cache at one point, removing anything after that point costs nothing extra.

R7L* = (overhead − w·(S − F)) / (r·(S − F))

Cheaper cache reads make helpers less attractive. A helper pays off only if the main agent has more than L* turns left (S: the reading, F: the answer that comes back). As read prices fall, keeping text becomes cheap and helpers need longer sessions to pay.

R8

When the cache has expired, removal is free. Everything is billed at full price either way, so that is the moment to clear small blocks.

R9

Edited files are expensive to keep early. A changed file makes every conversation holding the old version stale. The file being edited belongs late in the conversation, or in a short-lived one.

The theory it connects to

Below the threshold this is a known puzzle, ski rental with predictions: keep renting or buy, when you do not know how long you will need it, but you have a forecast (Purohit, Svitkina & Kumar, NeurIPS 2018). Our version adds a buy price that rises over time and free purchases when the cache expires; that variant is not covered by the existing theory. The agent's own plan is the forecast.

Step 5

Can our old logs test it?

We had 124 logged calls from earlier runs. Could they check the model?

No. They were accurate about what they recorded, but:

  • the provider reported the cached part on only 14% of calls, and that is the model's central number;
  • runs were 7 to 21 calls long, far too short;
  • nothing was ever removed, so there was nothing to test removal against;
  • the growth figure came from runs our own policy shaped, so testing on them would be circular.

They did teach one real thing: conversations grow in bursts, not steadily (one turn jumped by 12,517 tokens). A burst is one big tool result, exactly what placement cares about.

Changed on your direction. The plan here was to replay public agent transcripts through a simulated bill. You asked for real API runs only, so that real cost and real success are measured together. Step 6 is that study.
Steps 6 and 7

The live study

Real bug-fix tasks from open-source projects (SWE-rebench), real models through your Google key, prices from Google's list, each run checked by the task's hidden tests. Four policies: never remove, summarize, clear old outputs, and EconoContext.

  • Claude Sonnet 5 was skipped for now: Google needs a login for it, not the API key, and the project has no access yet. The code for it is written and tested.
  • Gemini 3.5 Flash was replaced by Gemini 3.6 Flash: Google's shared capacity refused most real requests to 3.5, while 3.6 accepted 10 out of 10.
  • gpt-oss-120b was skipped after three runs: Google's serving returns its tool calls as raw text most of the time.

The results are in the pilot report (in the repository: docs/runs/2026-09-25-live-study/report.html).
