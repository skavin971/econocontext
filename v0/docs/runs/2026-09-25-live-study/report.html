EconoContext Live Pilot

The first time EconoContext's idea met real software tasks, real models and a real bill. What we ran, what happened, and what it means.

The short answer

On Gemini 3.6 Flash, every policy solved both real bug-fix tasks, for 15 to 71 cents a run. EconoContext's policy cost the most, because it hands work to helper agents and underestimates what they cost. The tasks were also too short to test the part of the idea about removing old context. The pilot did its job: it found the weak spot, and nine bugs that would have spoiled a larger study.

What we were testing

One question, asked of real agents instead of a simulation.

A coding agent re-sends its whole conversation to the model on every turn, and the provider bills it every time. Providers discount the part they have seen before (a cache hit), but only when the start of the conversation is unchanged. So where a piece of information sits, and whether it ever enters the main conversation at all, changes the bill.

EconoContext's claim is that a harness can price those choices and make them better than the fixed rules agents use today. The pilot puts four policies side by side on the same tasks:

PolicyWhat it doesStands in for
P0 append-onlyNever removes anything.The simplest agent
P1 summarizePast 60K tokens, a paid model call summarizes the middle of the conversation.Claude Code auto-compact, OpenHands condenser
P2 clear oldPast 60K tokens, replaces all but the 3 newest tool outputs with [cleared].LangChain ClearToolUsesEdit
P3 EconoContextPrices every large tool result: keep it in the main conversation, or hand the reading to a short-lived helper agent that returns a summary. Removes old results only when the cache prices say it pays.Ours

How one run works

The pieces we built for this

  • Real tasks. Two bug-fix issues from real open-source projects (pyflakes and starlette_exporter), from the public SWE-rebench set. They were chosen by a rule fixed in advance: every published reference run of each took at least 50 turns and succeeded.
  • An agent that works inside the task's own environment. The repository is copied out of the task's Docker image; commands run in a container from that image.
  • Independent checking. The agent's change is applied in a fresh container and the task's hidden tests decide pass or fail. The agent saying it is done counts for nothing.
  • Real prices. Every call is priced from the provider's reported token counts at Google's list prices, read on 25 September 2026.
  • A hard budget. No run starts unless the remaining budget covers its whole cap, and no call starts if its worst case would cross the run's cap.

What the results say

Finding 1

Removing old context was never actually tested

P1 and P2 only act once the conversation passes 60,000 tokens. These runs peaked between 37,000 and 61,000. P1 summarized once, in one run; P2 never cleared anything; P3's cache-priced removal never fired. So P0, P1 and P2 were in effect the same policy, and their cost differences (15 to 31 cents) are the normal variation between two runs of the same model, not a policy effect.

The tasks were chosen for long reference runs (at least 50 turns), but our agent solved them in 27 to 45 calls with much shorter tool output. Turn count was the wrong proxy for context size. The next study should pick tasks by how many tokens a reference run accumulated.

Finding 2

EconoContext's helper agents cost more than they save

P3 handed reading to a helper agent 13 times on pyflakes and 9 times on starlette. The helpers took 68% and 47% of the bill. Meanwhile the main agent did about the same amount of work as without them: 49 calls against P0's 42, and 35 against 32.

  • The planner underestimates a helper. Its cost model assumes a helper takes 2 calls. The real average was about 7 on pyflakes and 3 on starlette, so every delegation looked cheaper than it was.
  • 11 of 22 helper tasks were thrown away. The helper's answer came back longer than its allowed size, was rejected, and the main agent got the original result anyway. Those helpers were paid for and used for nothing.

This matches the earlier ledger experiment, where delegation also lost on a task that fits comfortably. It does not refute the idea of pricing placement; it shows the prices the planner uses are wrong. Measuring what helpers really cost, and using those numbers, is the next step.

Finding 3

Reuse fired for the first time

On starlette, P3 answered three requests with a result it had already paid for instead of doing the work again. That decision had never been made in any earlier run of the project. It worked, and the task was solved.

Finding 4

Caching carries most of the saving already

Between 54% and 73% of all input tokens were cache hits in every run, billed at a tenth of the price. The simplest policy already gets the largest discount available, which sets a high bar for anything cleverer.

Bugs the pilot caught

Each would have quietly distorted a larger study. All are fixed and covered by tests (40 passing).

  1. Turn limit counted helper calls. P3's main agent got about half the turns of the others. The limit now counts the main agent only, for every policy.
  2. Parallel studies interrupted each other. They shared one database, and each startup marked the other's run as crashed. Every study now has its own. (15 runs lost, all at $0.)
  3. Task containers were left running. The harness shut down before a finished run removed its container; 19 built up. It now waits for cleanup.
  4. Busy refusals used up turns and ended runs. Now retried for about 3 minutes, not counted as turns, and a run killed by them is re-run once.
  5. gpt-oss tool calls arrived as text. Now recovered and marked, so their frequency is on the record.
  6. Sending reasoning back broke gpt-oss requests. Kept in our logs, no longer sent.
  7. Summaries could fail on a busy refusal. P1's summary call now retries like any other call.
  8. Worst-case cost check ignored cache-write prices. Now uses the higher of input and cache-write rates.
  9. A stale-file bug in Docker's file sharing made the second check of a task read the first check's files. Each check now gets a fresh folder.

Suggested next steps

For discussion. None has been started.

  1. Price helpers from measurement. Record what each helper actually costs and feed it back into the planner, instead of the fixed "2 calls" guess. Also cap or shorten helper answers so fewer are thrown away.
  2. Choose tasks that fill the context. Select by tokens accumulated in the reference runs, so the removal policies actually trigger.
  3. Run each cell more than once. One run per cell cannot separate a policy effect from ordinary variation; three to five can.
  4. Add Claude when access is sorted. Its cache charges for writes, which is where removal timing matters most.
